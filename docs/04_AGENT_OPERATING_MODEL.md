# 04. 에이전트 운영 모델

## 1. 운영 원칙

이 프로젝트는 한 에이전트가 모든 판단과 구현을 동시에 맡지 않는다. 주도 에이전트가 작업을 분해하고, 역할별 에이전트가 산출물을 만들며, 검수 에이전트가 독립적으로 통과 여부를 판단한다.

```text
사용자 요구사항
  ↓
주도 에이전트 ── 기획 에이전트
  ├────────── 아키텍처·보안 에이전트
  ├────────── 개발 에이전트
  ├────────── 기능검수 에이전트
  └────────── 운영·유지보수 에이전트
  ↓
사용자 승인 및 다음 Phase
```

에이전트는 필요할 때만 병렬로 사용한다. 같은 파일을 동시에 수정하지 않으며, 앞 단계의 계약이 정해지지 않은 상태에서 다음 단계 구현을 시작하지 않는다.

## 2. 역할과 책임

### 2.1 주도 에이전트(Lead/Orchestrator)

- 모든 문서와 `docs/08_REQUIREMENTS_INBOX.md`를 먼저 읽는다.
- 요구사항을 기능 ID와 테스트 ID로 연결한다.
- Phase를 작은 작업 단위로 나누고 담당 에이전트를 지정한다.
- 충돌 가능성이 있는 파일의 소유권을 조정한다.
- 검수 결과를 취합하되, 실패를 임의로 통과 처리하지 않는다.
- 사용자에게 구현 범위, 남은 위험, 비용 발생 여부를 보고한다.

필수 산출물:

- 현재 Phase 작업 계획
- 요구사항 추적표
- 변경 파일 목록
- 검증 결과와 다음 단계 진입 여부

### 2.2 기획·요구사항 에이전트(Product)

- 추가 요구사항을 모호함, 중복, 충돌 기준으로 분석한다.
- 사용자 흐름, 예외 흐름, 승인 기준을 구체화한다.
- 범위를 `필수 / 이후 / 제외`로 나눈다.
- 기능 ID(`F-xxx`)와 수용 기준을 갱신한다.

수정 가능 문서:

- `docs/01_MASTER_PLAN.md`
- `docs/02_FUNCTIONAL_SPEC.md`
- `docs/08_REQUIREMENTS_INBOX.md`

### 2.3 아키텍처·데이터·보안 에이전트(Architecture)

- 서버/브라우저 경계, 데이터 모델, 상태 전이, API 계약을 검토한다.
- OpenAI 키 노출, 중복 과금, 동시 실행, 장애 격리를 점검한다.
- 모델명·프롬프트·생성 옵션을 중앙 설정으로 유지하도록 설계한다.
- 마이그레이션과 백업·복구 가능성을 확인한다.

수정 가능 문서 또는 코드 영역:

- `docs/03_TECH_DATA_API.md`
- Prisma 스키마와 마이그레이션
- 서버 전용 AI 어댑터와 공통 설정

### 2.4 개발 에이전트(Implementation)

- 승인된 Phase의 최소 범위만 구현한다.
- UI, API, DB, 테스트를 함께 변경한다.
- 기존 사용자 변경과 무관한 파일을 수정하지 않는다.
- 생성 실패, 재시도, 빈 상태, 로딩 상태를 정상 흐름과 같이 구현한다.
- 변경 후 자체 검토와 자동 검증을 수행한다.

### 2.5 기능검수 에이전트(QA)

- 개발 에이전트와 분리된 관점에서 기능을 검사한다.
- 요구사항 문구가 아니라 실제 사용자 행동으로 검증한다.
- 한국어 글자, 패널별 인물 일관성, 대사 의미, 여백을 개별 항목으로 판정한다.
- 실패 재현 절차, 기대 결과, 실제 결과, 증거를 기록한다.
- 비용 발생 테스트는 승인된 제한 횟수 안에서만 실행한다.

검수 결과는 다음 셋 중 하나다.

- `PASS`: 필수 기준을 모두 만족
- `CONDITIONAL PASS`: 경미한 문제와 후속 조치가 명시됨
- `FAIL`: 사용자 흐름, 데이터, 보안, 비용 또는 핵심 품질 기준 위반

### 2.6 운영·유지보수 에이전트(Operations)

- 설치, 환경변수, DB 마이그레이션, 백업, 복구 절차를 검증한다.
- 로그에 키·전체 프롬프트·민감 데이터가 남지 않는지 확인한다.
- 의존성, 모델 변경, 장애 대응 기록을 관리한다.
- 릴리스 전 운영 체크리스트와 롤백 경로를 확인한다.

## 3. 작업 위임 양식

주도 에이전트는 역할 에이전트에게 다음 형식으로 작업을 전달한다.

```markdown
작업 ID: TASK-P{Phase}-{번호}
담당 역할:
목표:
입력 문서/파일:
수정 허용 범위:
금지 사항:
완료 조건:
실행할 검증:
보고 형식: 변경 내용 / 검증 결과 / 남은 위험
```

## 4. 인수인계 계약

모든 에이전트의 완료 보고에는 아래가 포함되어야 한다.

1. 어떤 요구사항 ID를 처리했는가
2. 어떤 파일을 왜 변경했는가
3. 실행한 검증과 결과는 무엇인가
4. 실패했거나 실행하지 못한 검증은 무엇인가
5. 비용이 발생했는가
6. 다음 담당자가 알아야 할 위험과 가정은 무엇인가

말로만 “완료”라고 보고할 수 없다. 자동 검증 결과와 필요한 화면 증거가 있어야 한다.

## 5. 단계 승인 회의

각 Phase 종료 시 주도·개발·검수·운영 관점을 합쳐 다음을 결정한다.

| 항목 | 질문 | 승인 주체 |
|---|---|---|
| 범위 | 승인된 요구사항만 구현했는가 | 주도/기획 |
| 구조 | 다음 Phase가 안정적으로 이어지는가 | 아키텍처 |
| 기능 | 핵심/예외 흐름이 실제로 동작하는가 | 기능검수 |
| 운영 | 설치·백업·복구·로그가 관리 가능한가 | 운영 |
| 비용 | 실제 API 호출 조건과 상한이 지켜졌는가 | 주도/운영 |

한 항목이라도 핵심 실패가 있으면 다음 Phase로 넘어가지 않고 동일 Phase에서 수정·재검증한다.

## 6. 작은 프로젝트에서의 축소 운영

동시에 여러 에이전트를 실행할 수 없는 환경에서는 아래 순서로 동일한 역할을 교대 수행한다.

```text
주도 계획 → 기획 검토 → 개발 → 독립 검수 모드 → 운영 검토 → 주도 승인
```

같은 에이전트가 역할을 교대할 때도 개발 직후 바로 통과 판정하지 말고, 변경 내역을 닫은 뒤 검수 문서만 기준으로 다시 검사한다.
