# 07. 운영·유지보수 계획

## 1. 운영 목표

- 개인 노트북이 바뀌어도 문서와 저장소만으로 복구할 수 있다.
- AI 서비스 장애와 갤러리·검색 기능을 분리한다.
- 비용, 생성 이력, 승인 이력을 사후 확인할 수 있다.
- 모델이나 프롬프트 변경이 기존 결과를 조용히 바꾸지 않는다.

## 2. 환경 분리

| 환경 | 용도 | AI 기본값 | 데이터 |
|---|---|---|---|
| local | 개발 | OFF 또는 MOCK | 로컬 SQLite |
| test | 자동 검증 | MOCK | 매 실행 격리 DB |
| production-like | 최종 검수 | 제한적 LIVE | 검수 전용 DB |

실제 서비스 배포 환경은 추가 요구사항으로 배포 대상을 확정한 뒤 별도 설계한다. 현 문서는 로컬 우선 운영을 기준으로 한다.

## 3. 비밀값과 설정

- `.env.example`만 저장소에 포함하고 실제 `.env`는 포함하지 않는다.
- `OPENAI_API_KEY`는 서버에서만 읽는다.
- 모델, 이미지 크기, 품질, WebP 품질, 동시 실행 수를 중앙 설정으로 관리한다.
- 시작 시 필수 설정을 Zod로 검사하되, AI가 OFF인 경우 키 누락 때문에 검색·조회 기능을 막지 않는다.
- 운영 로그에는 키, 인증 헤더, 전체 환경변수를 출력하지 않는다.

## 4. 데이터와 파일 배치

권장 런타임 구조:

```text
data/
  app.db
  backups/
storage/
  originals/
  webp/
  exports/
logs/
```

`data/`, `storage/`, `logs/`는 Git에서 제외한다. 샘플과 스키마만 저장소에 둔다.

## 5. 백업 정책

- DB 구조 변경 전 수동 백업
- LIVE 생성 또는 대량 이관 전 백업
- 중요한 작업 종료 시 날짜·시간이 포함된 DB 백업
- 생성 이미지와 export 메타데이터는 같은 백업 단위로 보관
- 최소 최근 5개 백업을 유지하되 실제 보존 기간은 운영 환경 용량에 맞게 확정

백업 이름 예시:

```text
backup-20260906-153000/
  app.db
  storage-manifest.json
  checksums.txt
```

## 6. 복구 절차

1. 앱과 쓰기 작업을 중지한다.
2. 현재 DB와 파일을 별도 폴더에 보존한다.
3. 선택한 백업의 체크섬과 파일 개수를 검사한다.
4. 임시 경로에서 DB를 먼저 열고 마이그레이션 호환성을 검사한다.
5. 프로젝트 조회, 이미지 경로, export JSON을 샘플 검증한다.
6. 검증된 백업만 운영 경로로 전환한다.
7. 복구 시간, 대상 백업, 검증 결과를 기록한다.

복구 명령은 구현 시 스크립트로 제공하고, 원본 DB를 직접 덮어쓰기 전에 항상 임시 복원 검증을 거친다.

## 7. 배포·업데이트 체크리스트

1. 승인된 요구사항과 변경 범위를 확인한다.
2. DB와 storage를 백업한다.
3. lint, typecheck, test, E2E, build를 실행한다.
4. 마이그레이션 내용을 검토하고 임시 DB에서 연습한다.
5. OFF/MOCK 모드로 앱을 기동한다.
6. 검색, 조회, 기존 결과 표시를 확인한다.
7. 필요한 경우에만 제한된 LIVE 검수를 실행한다.
8. 버전, 마이그레이션, 모델 설정, 알려진 제한을 릴리스 기록에 남긴다.

## 8. 장애 대응

### OpenAI 응답 지연 또는 실패

- 새 생성 요청을 실패 또는 재시도 가능 상태로 기록한다.
- 기존 검색·프로젝트·이미지 조회는 계속 제공한다.
- 자동 무한 재시도를 하지 않는다.
- 동일 요청을 재개할 때 기존 요청 키를 확인한다.

### 중복 생성 의심

- 해당 프로젝트의 생성 잠금을 유지한다.
- 요청 키, 시작 시각, 이미지 시도 기록을 비교한다.
- 결과를 삭제하지 않고 중복 여부를 표시한 뒤 검토한다.

### DB 또는 파일 불일치

- export를 중지한다.
- 최근 백업과 저장소 manifest를 비교한다.
- 원본 이미지를 삭제하지 않고 누락/고아 파일 목록을 만든다.

### 모델 품질 저하

- 모델명과 프롬프트 버전을 고정하고 변경 이력을 확인한다.
- 동일한 검수 샘플로 회귀 평가한다.
- 새 설정이 통과하기 전 기존 설정을 유지한다.

## 9. 유지보수 주기

| 주기 | 작업 |
|---|---|
| 매 변경 | 자동 검증, 브라우저 확인, 요구사항 추적 갱신 |
| 매 릴리스 | 백업/복구 샘플, dependency·migration 기록 |
| 월 1회 | 오래된 로그·실패 작업·고아 파일 점검 |
| 모델 변경 시 | 출력 스키마, 품질 샘플, 비용 안전장치 재검수 |

## 10. 변경 기록

유지보수 변경에는 다음을 기록한다.

```markdown
변경 ID:
날짜:
관련 요구사항/장애:
변경 전/후:
DB 마이그레이션 여부:
모델/프롬프트 변경 여부:
검증 결과:
백업과 롤백 위치:
담당 역할:
```
