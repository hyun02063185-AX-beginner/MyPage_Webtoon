# 09. 새 환경 시작 프롬프트

아래 내용을 새 개발 환경의 코딩 에이전트에게 그대로 전달한다. 이 기획 패키지 폴더와, 선택적으로 기존 이미지·용어 데이터만 함께 복사하면 된다.

## 첫 실행 프롬프트

```text
이 저장소에서 “AI·AX 용어 4컷 만화 생성기”를 처음부터 구축해줘.

먼저 이 순서로 문서를 전부 읽어:
1. README.md
2. AGENTS.md
3. docs/00_START_HERE.md
4. docs/01_MASTER_PLAN.md
5. docs/02_FUNCTIONAL_SPEC.md
6. docs/03_TECH_DATA_API.md
7. docs/04_AGENT_OPERATING_MODEL.md
8. docs/05_PHASE_PLAN.md
9. docs/06_TEST_ACCEPTANCE.md
10. docs/07_OPERATIONS_MAINTENANCE.md
11. docs/08_REQUIREMENTS_INBOX.md

이번 첫 작업에서는 Phase 0만 수행해. 바로 전체 기능을 코딩하지 마.

Phase 0에서 할 일:
- 추가 요구사항 입력함의 원문을 보존하면서 요구사항 ID와 수용 기준으로 정리
- 기존 기획과 충돌·중복·누락되는 부분 분석
- Must / Should / Could / 제외 범위 제안
- 기능 ID ↔ 요구사항 ID ↔ 테스트 ID 추적표 작성
- 새 환경과 저장소 상태 점검
- 고정 기술 스택을 기준으로 초기 폴더·설정 계획 제안
- 실제 OpenAI 호출 없이 비용 안전장치와 mock 전략 확인
- 에이전트 역할별 작업 분할안과 Phase 1 완료 조건 제시

중요 규칙:
- OpenAI 키는 서버 전용이며 브라우저 코드에 넣지 않는다.
- 시나리오 승인 전 이미지 생성 API를 호출하지 않는다.
- 연속 클릭, 새로고침, 재시도로 중복 과금되지 않게 설계한다.
- mock 결과는 명확히 표시하고 최종 갤러리 내보내기를 금지한다.
- 기존 100개 용어 검색은 AI 장애와 이미지 유무에 독립적으로 동작해야 한다.
- 기존 결과물은 원본을 보존하며 선택적으로 이관한다.
- 요구사항에 없는 기능을 임의로 추가하지 않는다.
- lint, typecheck, test, E2E, build 실패 상태를 완료라고 하지 않는다.
- 각 Phase마다 구현 → 검토 → 수정 → 재검증 후 다음 단계로 간다.

에이전트 운영:
- 주도 에이전트가 계획과 파일 소유권을 관리한다.
- 기획, 아키텍처·보안, 개발, 기능검수, 운영·유지보수 역할을 분리한다.
- 동시에 작업할 경우 서로 같은 파일을 수정하지 않게 한다.
- 기능검수 역할은 개발 결과를 독립적으로 재현하고 PASS/FAIL을 판정한다.
- 각 역할은 변경 파일, 검증 결과, 미해결 위험, 비용 발생 여부를 보고한다.

Phase 0 결과를 먼저 나에게 보고하고, 구현을 시작하기 전에 내 추가 지시를 기다려.
```

## Phase 1 이후 계속하기 프롬프트

사용자가 Phase 0 보고를 확인한 뒤 다음처럼 지시한다.

```text
정리된 요구사항과 추적표를 기준으로 Phase 1을 진행해줘.
docs/05_PHASE_PLAN.md의 범위를 넘지 말고, docs/04_AGENT_OPERATING_MODEL.md에 따라 역할을 분리해.
완료 전에 docs/06_TEST_ACCEPTANCE.md의 해당 검증을 실행하고 결과와 남은 위험을 보고해.
실패가 있으면 같은 Phase에서 수정하고 재검증해. 실제 OpenAI 호출은 하지 마.
```

Phase 4에서 실제 생성 검수가 필요할 때만 호출 횟수와 예상 범위를 먼저 정하고, 사용자가 LIVE 검수를 명시적으로 지시한 경우에 수행한다.

## 기존 자료를 함께 옮길 때

- 원본 이미지 폴더는 `legacy-input/images/`처럼 새 저장소와 분리한다.
- 기존 용어 데이터는 `legacy-input/data/`에 읽기 전용 원본으로 둔다.
- 원본 파일을 직접 수정하거나 이름을 일괄 변경하지 않는다.
- Phase 7 전에는 새 시스템의 운영 데이터로 간주하지 않는다.
